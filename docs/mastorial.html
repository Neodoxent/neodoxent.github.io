I. Purpose

The Mastorial is the system's memory. It is the place where architecture, doctrine, code behavior, symbolic grammar, and development direction are preserved together. Its purpose is not merely to document what exists, but to prevent the system from expanding into incoherence.

Core Purpose The Mastorial makes the system legible to its future author, future collaborators, future tools, and future audits. If the Meta-Landing is the console, the Mastorial is the architect's manual beneath the console.

Every time the interface changes meaningfully, this file should be updated. The Mastorial is not a static README; it is a living control document. Its function is to preserve the full thread of the system so that new additions can be judged against the whole, not against the excitement of the moment.

II. System Definition

The Neodoxent Infotech Interface Layer is a state-driven, recursive, symbolic interface system designed to prepare readers for structured exposure to Ascendancy. It is a website, but it is not merely a website. It borrows from dashboards, incremental interfaces, symbolic cards, ritual thresholds, archives, and knowledge maps, but it should never reduce itself to any one of those forms.

Primary Definition The system does not simply reveal content. It changes the reader's state until the reader has enough orientation, coherence, and symbolic literacy to receive deeper content.

What It Is

  • A cognitive instrument.
  • A recursive interface architecture.
  • A semiotic access layer into Ascendancy.
  • A stateful console for progressive orientation.
  • A public-safe bridge into deeper books, artifacts, concepts, and protocols.

What It Is Not

  • It is not a conventional game.
  • It is not therapy, diagnosis, instruction, or empirical proof.
  • It is not a shallow portfolio.
  • It is not an ARG or puzzle-box meant to confuse the reader.
  • It is not the whole Ascendancy system compressed into a page.

III. Architecture Stack

The system is deliberately modular. Each file has a role. This separation prevents the page from becoming an unmaintainable monolith. 

recursion.html        → Interface vessel / Meta-Landing chamber
assets/js/main.js     → Renderer, binder, unlock executor
assets/js/modules.js  → Unlock grammar and module doctrine
assets/js/state-engine.js → State, qBits, strata, resonance, manifest factor
docs/mastorial.html   → Master guide and system memory
Separation Rule HTML should not define system logic. CSS should not define doctrine. JavaScript should not invent meaning without modules.js. The Mastorial explains why the system exists and how every layer should behave.

Cybernetic Loop

User Action
→ State Update
→ Interpretation
→ Unlock Evaluation
→ Interface Update
→ Feedback
→ User Action

This loop is what makes the interface cybernetic. It is not static content delivery. The system responds to the reader's interaction history and modifies what becomes available.

IV. Entry Structure

The public site originally began as a threshold sequence. That sequence still matters. The Meta-Landing, however, is now becoming the recurring entry point for returning users. 

index.html      → Public articulation / landing surface
threshold.html  → Ethical and interpretive boundary
starfold.html   → Stabilization field
recursion.html  → Meta-Landing Console / recurring interface
Law of Entry Initiation happens once. Recurrence happens through the Meta-Landing.

The user should not be forced to re-read the full public landing and threshold warnings every time they return. Instead, the recurring interface should preserve orientation while allowing direct re-entry into the living system.

VII. Hidden Modifiers

The system now contains hidden adaptive modifiers. These should remain subtle. They are not rewards. They are field modifiers.

Resonance

Resonance is a behavior-sensitive modifier. It rises with slower, more deliberate engagement, stronger coherence, and stabilized orientation. It resists frantic clicking. 

slow engagement + coherence + orientation → resonance

Manifest Factor

Manifest Factor is the roundabout emergent modifier. It measures cross-domain readiness: how widely the reader has spread through qBits and strata, and how much entanglement and resonance have accumulated. 

qBit spread + strata spread + resonance + entanglement → manifestFactor
Design Function Resonance modifies behavior. Manifest Factor modifies structure. Together, they let the interface feel emergent without becoming arbitrary.

VIII. Progression, Pacing, and Nested Segments

The current system can unlock too quickly. That is acceptable for a prototype, but not for the mature interface. Each module needs internal segments and dwell-time gates.

Current Progression

accept → grant → update → unlock

Target Progression

enter module
→ read segment
→ dwell
→ complete subsegment
→ integrate
→ acknowledge
→ unlock next module

Planned Segment Structure

Segment 1 — Orientation
Segment 2 — Core Principle
Segment 3 — Expansion
Segment 4 — Integration
Segment 5 — Acknowledgment
Pacing Rule Fast progression breaks the system. The mature interface should require a few minutes of real engagement per module before the next module appears.

This does not mean the system should trap the user. It means the interface should respect cognitive pacing. The user should feel that modules are presented, not dumped.

XIII. Codex / Agent Use Policy

Codex or other coding agents can help audit, refactor, and improve the implementation. They should not be treated as the symbolic architect unless given this Mastorial as context.

Use Codex For

  • Bug detection.
  • Code refactors.
  • Performance and accessibility checks.
  • File splitting and cleanup.
  • Syntax validation.

Do Not Use Codex For

  • Doctrinal decisions.
  • Symbolic meaning.
  • Ascendancy architecture.
  • Field semantics.
  • Naming of sacred or hidden layers.
Codex Law Codex executes. We architect. The Mastorial remembers.
